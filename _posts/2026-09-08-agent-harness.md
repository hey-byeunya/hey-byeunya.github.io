## 무엇을 만들었나

수업 과제로 **에이전트 하네스**를 직접 만들었습니다. 하네스는 모델의 말을 실제 실행으로
연결하고 그 결과를 다시 모델에게 돌려주는 프로그램이에요.

만든 것은 제 강의 노트에서 주제를 찾아 **출처와 함께** 정리해 주는 로컬 CLI입니다.

```bash
python3 -m harness "어텐션 관련 내용을 노트에서 찾아 정리해줘"
```

```
[1] search_notes(keyword='어텐션') → ok (4/7개 파일에서 발견)
[2] read_note(path='트랜스포머_복습노트.html', section=3) → ok (459자)
...
어텐션은 Q(질문)·K(색인)·V(내용)로 "지금 토큰을 이해하려면 누구를 참고할지"를 계산합니다.
(출처: 트랜스포머_복습노트.html / 3번째 절 "잊지 말아야 할 것 6가지")
```

노트가 HTML과 Markdown으로 섞여 여러 파일에 흩어져 있어서, 어느 파일에 있었는지 다시 못 찾는
게 원래 불편했던 점이었어요. 그걸 해결하려고 만들었습니다.

---

## 배운 것 다섯 가지

### 1. 모델은 손이 없어요

유리방 안에 앉은 사서를 떠올리면 됩니다. 머리는 아주 좋은데 방 밖으로 손을 뻗을 수 없고,
할 수 있는 건 말뿐이에요. "그 파일 좀 읽어줘"라고 말할 수 있지만 그 말만으로 제 컴퓨터의
파일이 열리지는 않죠. **밖에서 실제로 서가에 가는 사람**이 필요하고, 그게 하네스입니다.

그래서 이 셋은 전부 다른 사건이에요.

```
모델이 "read_note 실행해줘"라고 요청함     ← 표현일 뿐
하네스가 인자와 경로를 검사함              ← 여기서 막힐 수 있음
하네스가 실제로 파일을 엶                  ← 이게 실행
```

### 2. "읽었습니다"는 증거가 아니에요

모델은 파일을 안 읽고도 그럴듯하게 *"복습노트를 확인해보니 어텐션은…"* 이라고 쓸 수 있습니다.
그래서 **답변 문장이 아니라 실행 기록만 증거로 삼도록** 만들었어요.

```
runs/task_20260908-160227.jsonl
  사용자 요청 → 모델 요청 전송 → 도구 요청 수신 → 인자 검사 →
  경로 검사 → 실행 → 결과 반환 → 최종 답 수신 → 종료
```

검증 기준도 "출처 표시가 있다"가 아니라 **"표시된 출처가 실행 기록에 있고 원문과 맞는다"** 로
잡았습니다.

### 3. 지시문은 부탁이고, 코드는 장치예요

이게 가장 크게 배운 것 같습니다. 지시문에 아무리 "이렇게 해라"라고 써도 모델은 무시할 수 있어요.
실제로 강제되는 건 코드에서 검사하는 것뿐입니다.

```
지시문: "노트 폴더 밖은 읽지 마세요"          → 부탁
코드:   정규화한 최종 경로가 폴더 안인지 검사   → 장치
```

거절 검증도 마찬가지예요. **"거절 문구를 출력했다"로는 부족하고 "파일을 실제로 열지 않았다"를
봐야 합니다.** 실행 기록에 `실행` 단계가 아예 없는 것으로 확인했어요.

### 4. 실패도 기능입니다

"파일을 읽을 수 있다"만 적으면 파일이 없을 때가 안 정해져요. 그래서 실패 동작을 처음부터
명세에 넣었습니다.

| 상황 | 동작 |
|---|---|
| 파일 없음 | 오류를 모델에게 돌려주고 다른 경로를 시도할 기회를 줍니다 |
| 허용 범위 밖 | 실행하지 않고 거절을 기록에 남깁니다 |
| 인증 실패 | 즉시 중단합니다 (도구 결과를 더 보내도 해결되지 않으니까요) |
| 반복 상한 도달 | **"완료"가 아니라 "제한에 도달해 중단"** 으로 표시합니다 |

특히 마지막이 중요했어요. 멈춘 걸 완료로 표시하면 그때부터 모든 기록을 못 믿게 됩니다.

### 5. 종료 조건을 모델에게 맡기지 않습니다

모델이 계속 도구를 요청하면 프로그램도 계속 돌 수 있어요. 그래서 상한을 코드에 뒀습니다.

```
도구 호출 8회 · 전체 120초 · 같은 거절 3회 → 각각 다른 사유로 종료
Ctrl+C → cancelled (사유 user_cancelled, 종료 코드 130)
```

사용자 취소·정책상 중단·진행 불가를 **서로 다른 상태로** 기록해요. 하나로 뭉뚱그리면 나중에
원인을 못 찾습니다.

## 조심할 것 — 제가 실제로 겪은 결함 11개

측정하면서 하나씩 드러난 것들입니다. 전부 점수가 아니라 **실행 기록에서** 찾았어요.

### ① 도구 결과를 그대로 파일에 쓰지 마세요 — 이중 이스케이프

모델이 JSON 내용을 보낼 때 줄바꿈을 **문자 그대로 `\n`** 으로 넣은 적이 있었습니다.

```
정상:  실제 개행 22개 · 문자 "\n" 0개   → json.load OK
문제:  실제 개행  0개 · 문자 "\n" 49개  → json.load 실패 → 채점 0점
```

`write_file`이 아무 신호 없이 받아들이고 있었어요. 지금은 감지해서 거절합니다.

### ② 같은 파일을 계속 다시 쓰는 걸 막으세요

한 시행이 **동일한 파일을 13번** 썼습니다. 토큰만 태우고 진전이 없죠. 같은 경로 + 같은 내용은
거절하고 "확인한 문제를 실제로 고친 내용을 쓰라"고 되돌려 보냅니다.

### ③ 대화 크기 상한이 없으면 조용히 부풀어요

한 시행이 모델 호출당 9,355 토큰까지 커졌습니다(총 346K). 상한을 두고 넘으면 `context_limit`
사유로 멈추게 했어요. 참고로 **문자 수 상한은 모델의 토큰 한도와 다르고, 자동 요약도
아닙니다.**

### ④ 오류 메시지에 방향 정보를 담으세요

`file_not_found`만 돌려주면 모델은 경로를 헤매기 시작합니다. 실제로 도구 호출의 **7%가
없는 경로 탐색**에 쓰였고, 두 시행은 그것만 하다 단계를 다 써버렸어요.

```json
{ "error": "file_not_found",
  "workspace_top": ["app/", "db/", "home/"],
  "nearest_existing": { "path": "app", "entries": [] } }
```

이렇게 바꾸니 낭비가 7.0% → 4.3%로 줄었습니다. **정답을 알려주는 게 아니라 도구가 자기
허용 범위를 알려주는 것**이에요.

### ⑤ 같은 인자의 읽기 반복을 막되, 무효화를 잊지 마세요

읽기 도구를 같은 인자로 다시 부르면 같은 답이 옵니다. 한 시행이 `list_files`를 **35번**
반복해 40회 상한을 소진했어요.

다만 무조건 막으면 정상 작업이 깨집니다. **파일을 쓴 뒤 다시 조회하는 건 당연한 행동**이니까요.
그래서 `write_file`·`run_python` 뒤에는 기억을 비웁니다. 이 무효화가 핵심이었어요.

### ⑥ 평가기가 주는 값의 의미를 왜곡하지 마세요

가장 아팠던 실수입니다. 평가기가 `task_cwd`를 주는데, 그건 **파이썬이 실행되는 위치**일 뿐
산출물을 둘 곳이 아니에요. 그런데 저는 그걸 "과제 작업 디렉터리"라고만 적어 넘겼습니다.

모델이 그걸 경로 접두어로 해석해 `workspace/app/resolver.py`에 파일을 썼고, 채점기는 `app/`만
보니 못 찾아서 **0/13**이 됐어요.

> **지시를 충실히 따르는 모델일수록 제 왜곡에 크게 다쳤습니다.**
> 약한 모델은 그 줄을 무시해서 오히려 점수가 나왔어요.

그리고 문구로 두 번 고쳤는데 **문항마다 방향이 반대로** 나왔습니다. 결국 문구가 아니라 코드에서
경로를 정규화했어요 — 요청이 작업 폴더 이름으로 시작하고 **벗긴 쪽에만 대상이 존재할 때에만**
벗깁니다. 실제로 있는 경로는 절대 가로채지 않아요.

### ⑦ 이진 출력이 예외를 던져 시행 전체를 죽였어요

`subprocess.run(text=True)`는 기본이 **strict UTF-8 디코딩**입니다. 압축기 과제가 이진
데이터를 표준출력으로 내보내는 순간 `UnicodeDecodeError`가 터졌어요.

더 나빴던 건 이 예외가 도구 밖으로 나가서 **채점조차 실행되지 않았다**는 점입니다
(`verifier_result: null`). 실패 기록도 안 남았어요.

```python
subprocess.run(..., text=True, errors="replace", ...)
```

`read_file`에는 `errors="replace"`를 넣어뒀는데 `run_python`에는 빠져 있었습니다.
**같은 실수를 한 곳에서만 피한 거예요.** 이런 게 제일 잡기 어렵습니다.

### ⑧ 예외를 밖으로 흘리지 마세요

⑦의 교훈이에요. 진입점 함수는 **어떤 예외도 밖으로 내지 않고** 실패 상태로 돌려줘야 합니다.

```python
except Exception as err:
    return {"status": f"harness_error:{type(err).__name__}", ...}
```

**실패를 성공으로 바꾸는 게 아니라, 실패가 기록되게 만드는 것**입니다. 상태가 `completed`가
아니니 평가기는 미완료로 기록하고, 채점은 정상 실행돼요.

### ⑨ 탐색만 하고 작업을 시작하지 않는 패턴

⑤로 같은 인자 반복은 막았는데, **매번 다른 경로**로 40회 탐색하는 건 그대로 통과했습니다.
파일을 하나도 못 쓰고 끝났어요.

상한은 데이터로 정했습니다 — 130 시행에서 정상 작업의 최대 연속 목록 조회는 **0~5회가 93%**,
헛돌던 시행은 28~40회였어요. 그래서 8회를 상한으로 잡았습니다.

여기서도 경계가 중요했어요. **읽기 자체를 막으면 안 됩니다.** `read_file`을 22회 쓴 시행이
만점을 받았거든요. 그래서 "폴더 목록만 연속으로 보는 것"만 막습니다.

### ⑩ 종료 코드 0이 "성공"을 뜻하지 않습니다

모델이 함수만 정의하고 **호출하지 않는 스크립트**를 만들어 실행했어요.

```python
def convert_json_to_csv(input_path, output_path):
    ...
    with open(output_path, 'w') as out:   # 쓰는 코드는 있어요
        ...
# 파일 끝 — if __name__ == "__main__" 도, 호출도 없습니다
```

결과는 `종료 코드 0 · stdout 0자 · stderr 0자`. 모델은 성공으로 읽었고, 산출물은 없었죠.
이 문항은 **27시행 중 22회가 0점**이었습니다.

고친 방법은 실행 전후로 작업 폴더를 비교해 `files_changed`를 함께 돌려주는 거예요.

```json
{ "exit_code": 0, "files_changed": [],
  "note": "종료 코드가 0이지만 출력도 없고 바뀐 파일도 없습니다.
           스크립트가 함수만 정의하고 호출하지 않았을 수 있습니다." }
```

**종료 코드를 조작하지 않고 사실만 덧붙입니다.** 그러니까 모델이 호출 스크립트를 새로 만들어
실행하고 결과를 확인하기 시작했어요. 0점이 사라지고 88~89점대가 됐습니다.

### ⑪ 사용량을 모르는 것과 0인 것은 달라요

토큰 사용량이 응답에 없을 때 0으로 채우면 "무료로 썼다"로 읽힙니다. `usage_known: false`로
내리고, 보고서는 모든 시행에서 알려졌을 때만 총량을 표시하게 했어요.

## 그리고 가장 큰 교훈: 1회 실행으로는 아무것도 말할 수 없어요

처음에 기준 성능을 **1회씩** 재서 20%를 얻었습니다. 개선하고 다시 재니 0%가 나와서
"가설 기각"이라고 적었어요.

그런데 **같은 코드로 3회씩 다시 재보니 기준이 원래 10%였습니다.** 1회 실행에서 통과했던 문항이
3회 모두 실패했어요. 20%는 운이었던 거죠.

같은 코드·같은 모델로 한 문항이 이만큼 흔들렸습니다.

```
lz77 압축기     1 · 2 · 33 · 41 · 50 · 82 · 85 / 85
JSON→CSV       0 · 67 · 0 / 90
```

**한 문항 안에서 0점과 70점이 오갑니다.** 그러니 1~2문항 차이는 개선의 증거가 되지 못해요.
제가 초반에 자신 있게 내린 "기각"과 "역효과" 판단은 대부분 이 변동을 보고 있었습니다.

그래서 판정 기준을 바꿨어요.

| 판정할 수 있는 것 | 판정할 수 없는 것 |
|---|---|
| 파일이 어디에 쓰였나 (관측값) | 통과 수 ±1~2 |
| 3회 모두 0점 → 3회 모두 만점 | 검사 점수 소폭 이동 |
| 예외로 채점조차 안 되던 것 → 정상 실행 | 어느 회차가 더 나은가 |
| 거절이 몇 번 실제로 발동했나 | |

## 최종 결과와 정직한 한계

상위 모델 선택 · 문항당 3회 · 분모 30

| | 성공 시행 | easy | medium | hard |
|---|---|---|---|---|
| 기준 | 5/30 = 16.7% | 2/6 | 0/12 | 3/12 |
| 개선 | 9/30 = 30.0% | 3/6 | 3/12 | 3/12 |

**+4시행 중 3시행이 한 문항에서 나왔습니다.** 그 문항은 `task_cwd` 의미를 바로잡으니
`0/30 ×3` → `30/30 ×3`이 됐어요 — 양쪽 3회가 완전히 일관되니 변동이 아닙니다.
나머지 1시행은 변동 범위 안이에요. **"거의 두 배"라고 말할 수 없습니다.**

그리고 결함 11개를 고친 뒤에도 **통과 수는 30%에서 더 오르지 않았습니다.** 이유는 분명해요.
남은 실패의 성격이 바뀌었기 때문입니다.

```
초기: 파일이 엉뚱한 곳에 · 실행이 안 됨 · 예외로 죽음   → 하네스 결함 (고쳤어요)
지금: 88/90 · 11/13 · 9/10 · 19/22                   → 명세 세부를 놓침
```

실패한 검사를 열어보니 `assert 'True' == 'true'` 같은 것이었어요. 파이썬 `True`를 그대로
문자열로 쓴 것. 하네스가 도구·경로·실행을 제공하는 층과 다릅니다. **여기서 점수를 더 올리려면
하네스가 아니라 모델이나 지시문을 건드려야 하고, 그건 조건 변경이에요.**

실제로 하네스는 그대로 두고 **상위 모델로 바꿔** 재보니 한 문항이 `0/30` → `30/30 만점`이
됐습니다. 그 벽은 하네스가 아니라 모델이었던 거죠. 다만 상위 모델이 모든 문항에서 낫지는
않았어요 — 오히려 낮아진 문항도 있었습니다.

마지막으로 밝혀 둘 게 있습니다. 같은 10문항을 보며 11번 개선했으니 이 문항들은 이미
**개발용 평가 집합**이에요. 여기서 관찰한 변화를 처음 보는 작업으로 넓힐 수 없습니다.
그리고 이 점수는 원본 벤치마크의 **로컬 이식판 결과**이지 공식 점수가 아닙니다.

## 돌아보며

점수는 크게 오르지 않았어요. 그런데 이 실습에서 실제로 얻은 건 다른 것 같습니다.

- **"돌아간다"와 "근거가 있다"는 다릅니다.** 모델이 그럴듯하게 답하는 것과 실제로 파일을 읽은
  것은 별개고, 그걸 구별하려면 실행 기록이 필요해요.
- **부탁과 장치를 구별하는 감각.** 지시문에 쓴 건 지켜지지 않을 수 있고, 코드에서 검사한
  것만 지켜집니다.
- **측정 없이 개선을 말하지 않기.** 제가 초반에 자신 있게 내린 판단 대부분이 1회 실행의
  변동이었어요. 3회씩 다시 재고 나서야 무엇이 실제 개선인지 갈렸습니다.
- **오류 메시지가 인터페이스입니다.** `file_not_found`에 방향 정보를 넣는 것만으로 모델의
  행동이 바뀌었어요. 오류를 "실패 통보"가 아니라 "다음 행동의 재료"로 설계해야 합니다.

이 구조를 계약서·이용약관 같은 **버전 관리가 필요한 문서**나, 제안서부터 산출물까지 이어지는
**프로젝트 문서 흐름**에도 써볼 수 있을 것 같아요. 어느 판본을 근거로 답했는지가 중요한
자리니까요. 다만 문서를 고치는 작업이라면 승인 절차가 필수가 되고, 판본을 오가려면 세션
재개가 필요해서 설계를 다시 열어야 합니다.
